PROJECT 02 · 실무

학교급식 주문 일괄처리 · 주문변경내역 정합성 개선

2026.06 ~ 2026.10

배경 지자체 공공급식 센터가 학교 식재료 주문을 관리하는 시스템입니다. 센터가 수천~수만 건의 주문을 한 번에 확정(일괄처리)하고 나면, 영양교사 화면의 주문변경내역이 원래 주문 아래로 묶이지(트리) 않았고, "최초 주문확정 금액 + 변경 차액 = 최종 구매 금액"도 학교마다 맞지 않았습니다. 금액을 믿을 수 없으면 정산도 믿을 수 없기 때문에, 화면을 고치는 대신 데이터가 쌓이는 지점부터 다시 봤습니다.

참여 미참여 · 예정

원인을 좁혀 간 과정

  1. 트리가 안 생긴 이유 — 주문변경내역은 "주문확정 이력"을 트리의 뿌리로 씁니다. 그런데 일괄처리 프로시저는 주문 상태만 바꾸고 확정 이력을 남기지 않았습니다(한 건씩 확정할 때는 남김). 일괄처리된 주문은 뿌리가 없어 트리에서 빠졌습니다.
  2. 이력을 남기되 느려지지 않게 — 한 건씩 이력 프로시저를 부르면 수만 건에서 처리 시간이 크게 늘어납니다. 그래서 확정과 같은 흐름 안에서 INSERT … SELECT로 이력을 한 번에 기록하고, 순번은 PK 인덱스를 타는 방식으로 계산했습니다. 3만 건 넘는 일괄처리가 이력 기록을 포함해 1분 안에 끝납니다.
  3. 트리 기준 정리 — 과거 데이터처럼 확정 이력이 없는 주문도 보이도록 뿌리를 "주문확정 → 일반 최초 이력 → 추가 주문" 순으로 정했습니다. 그러자 변경 1건 때문에 같은 품목의 한 달치 주문 30건이 트리로 끌려오는 문제가 생겨, 실제 변경 · 추가 · 취소가 있는 주문만 조회하도록 바꿨습니다. 센터가 직접 고친 건은 "(센터)"로 구분해 표시했습니다.
  4. 금액 정합성 — 최초 금액 누락(조건이 너무 좁음, 151건 중 95건), 추가 주문의 이중 반영, 취소 건의 이중 차감을 차례로 찾았습니다. "최초 주문확정 금액은 이후 변경 · 취소가 있어도 바뀌지 않는다"는 규칙을 먼저 정하고, 네 가지 조회 조건에서 같은 값이 나오는지로 검증했습니다. 마지막 차이는 센터관리자가 확정 화면에서 수량을 직접 고친 단 1건이었습니다.

기술 선택

기술어디에왜 이것을 (쉽게)

선택 근거

  • 건별 호출 대신 집합 처리: 이미 3만 건 규모의 일괄처리 사례가 있어, 처음부터 대량 기준으로 설계했습니다.
  • 요약은 별도 조회: 목록에 가짜 요약 행을 섞지 않고, 요약 금액만 따로 조회해 화면 상단에 표시했습니다.
한계와 확장
  • 이력 기록 이전의 과거 데이터는 "추가 주문을 제외한 첫 원주문 이력"으로 보정했습니다. 보정 규칙과 대상 건수는 반영 SQL에 남겼습니다.
  • 같은 패키지의 품의 일괄처리는 월 단위로 5분가량 걸려, 원인(행마다 매칭 함수 2회 호출, 학교별 순차 호출)을 분석해 두었습니다. 다음 개선 대상입니다.

#1검색할수록 느려지다 429 — 페이지마다 처음부터 다시 부르고 있었다연구자 포털 · ScienceON 검색›
증상
첫 검색이 10초 이상, 뒤 페이지로 갈수록 느려지다 429 E4290(요청 한도 초과), 이어서 500 E5001
원인
  • 검색 1건에 제목 · 저자 · 저널 필드를 따로 3번 호출
  • N페이지를 보려고 1~N페이지를 매번 다시 조회해 이어 붙임
  • 논문유형 필터를 위해 한 번에 100건씩 대량 요청
해결
  • 통합 검색 필드 1회 호출(결과가 없을 때만 제목 검색 1회 추가)
  • 현재 페이지만 1회 호출, 같은 조건 · 페이지는 캐시
  • 요청 크기를 화면 크기(10건)로, 중간에 500이 나면 이미 받은 결과로 응답
왜 이렇게
미리 50건씩 받아 캐시하는 방식도 시도했지만 첫 검색이 더 무거워졌습니다. 연구자는 앞 페이지 위주로 보므로, 선조회보다 "필요한 만큼만 호출"이 맞다고 판단해 되돌렸습니다.
결과
검색 1건당 호출 3회 → 1회, N페이지 이동 시 N회 → 1회. 이후 요청 한도 오류 없이 운영 중입니다. 남은 한계는 필터 검색의 전체 건수가 추정값이라는 점입니다.
#2응답은 200, 총 42건인데 화면은 0건 — 응답 구조를 잘못 읽고 있었다연구자 포털 · ScienceON 검색›
증상
에러 없이 검색 결과만 비어 있음. 실서버에서만 재현
원인
응답이 <item metaCode="CN">처럼 속성으로 필드를 구분하는 구조인데, 파서는 <cn> 같은 태그 이름만 찾고 있었음 (네임스페이스도 미처리)
해결
호출 URL · 응답 코드 · 건수 · 파싱 결과를 단계마다 로그로 남겨 실서버 로그를 받고, TotalCount=42인데 파싱 결과 0건인 지점을 확인. metaCode 방식과 네임스페이스를 처리하도록 파서 수정
왜 이렇게
로컬에서는 테스트 토큰 권한 문제로 같은 응답을 받을 수 없어서, 추측으로 고치지 않고 실서버에서 "어디까지 정상인지"를 먼저 보이게 했습니다.
배운 점
에러가 없는 0건은 "호출 → 응답 → 파싱 → 화면" 중 어디서 사라지는지부터 나눠 봐야 합니다.
#3상태조회가 늘 "이력 없음", 고치고 나니 처리 중인 건이 완료로 — 상태 판정 바로잡기연구자 포털 · RapidILL SOAP›
증상
① 실제로는 처리 이력이 있는데 항상 "No history returned" ② 완료인데 원문 URL이 비어 있음 ③ 전송 직후 '전송완료'가 '대기'로 되돌아감 ④ 처리 중인 건이 완료로 표시
원인
  • ① 생성된 SOAP 클래스의 이력 반환형이 배열이 아니라 래퍼 객체였는데 배열로 처리
  • ② 매뉴얼상 redirect URL은 특정 조건에서만 반환. 실제 열람 URL은 다른 필드에 있음
  • ③ 전송 직후 바로 상태조회를 해 외부에서 아직 접수 전 상태를 받음
  • ④ redirect URL이 있으면 완료로 올리는 보정 로직
해결
  • 래퍼 객체의 리스트를 읽고, 마지막 이력의 상태 · 일시로 최종 상태 판정
  • 원문 URL 저장 우선순위를 매뉴얼 · 공식 안내 메일 기준으로 재정렬
  • 전송 직후 즉시 조회 제거
  • FILLED / FINISHED일 때만 완료로 판정
왜 이렇게
"전송완료 다음에 대기로 바뀌는 건 업무 흐름상 이상하다"는 점에서 출발했습니다. 처리 중 · 완료 두 건의 실제 응답 로그를 나란히 비교해 ④의 원인을 찾았고, 외부 관리 화면의 실제 이력과 대조해 ①을 확정했습니다.
배운 점
외부 시스템의 상태는 "있을 법한 값"으로 추정하지 말고 매뉴얼과 실제 응답으로만 판정해야 합니다.
#4"Invalid ISSN"으로 신청 반려 — 두 개의 ISSN이 하나로 붙어 있었다연구자 포털 · ScienceON → RapidILL›
증상

원인
ScienceON이 인쇄본 · 전자본 ISSN을 ;0128-1976;2289-4365; 형태로 주는데, 정규화 함수가 세미콜론을 모두 지워 두 값이 합쳐짐
해결
  • 값을 분리해 하나를 선택하고 선택 내역을 로그로 남김
  • ISSN 형식(^\d{4}-\d{3}[\dXx]$)을 화면과 서버 양쪽에서 검증, 화면 우회 제출도 서버에서 차단
왜 이렇게
매뉴얼에서 ISSN과 ISBN이 별개 필드라는 것을 확인해 "ISBN이 섞였다"는 가설을 버렸습니다. 외부 신청은 반려되면 연구자가 다시 작성해야 하므로, 보내기 전에 막는 쪽을 택했습니다.
결과

#5개발서버에서만 "서버 응답이 비어 있습니다" — Java 17에 없는 SOAP 클래스연구자 포털 · 배포 환경›
증상
로컬은 정상인데 개발서버에서 전송 버튼을 누르면 빈 응답, 상태조회는 한참 무반응
원인
서버 로그의 NoClassDefFoundError: javax.xml.ws.Service — Java 11부터 JDK에서 빠진 JAX-WS · SOAP 런타임이 개발서버(Java 17)에 없었음. 오류가 컨트롤러 밖으로 터져 응답이 비었음
해결
  • SOAP · JAXB 라이브러리를 배포본에 포함
  • SOAP 연결 10초 · 응답 15초 타임아웃
  • 컨트롤러가 어떤 오류든 JSON으로 응답하고, 화면은 빈 응답 · HTTP 오류 · JSON 오류를 구분해 안내
왜 이렇게
라이브러리만 넣으면 이번 오류는 사라지지만, 다음에 다른 오류가 나도 사용자가 "빈 화면"을 보게 됩니다. 그래서 원인 수정과 함께 실패해도 이유가 보이는 응답 구조로 바꿨습니다.
배운 점
로컬과 서버의 JDK 버전 차이는 컴파일이 아니라 실행 시점에 드러납니다. 이후 "로컬 확인 → 승인 → 개발서버 반영" 순서를 고정했습니다.
#6개발망에서 외부 API가 전부 타임아웃 — 코드가 아니라 방화벽이었다연구자 포털 · Jenkins / Kubernetes›
증상
새 개발망 배포 후 ScienceON 토큰 발급 Connect timed out, RapidILL Failed to access the WSDL … Connection timed out. 게다가 Jenkins에서 로그가 제대로 보이지 않음
원인
  • 로그: 배포 시점 로그만 한 번 읽고 끝났고, 라벨 조회가 종료 중인 이전 Pod 로그와 섞임
  • 연동: 두 외부 서비스 모두 TCP 연결 단계에서 실패 → 개발망 outbound 방화벽 미허용
해결
  • 새 Pod만 지정해 준비 완료를 기다린 뒤 실시간 로그(logs -f)를 일정 시간 추적하도록 Jenkins 수정
  • 외부 도메인 · 포트(TCP 443)를 정리해 방화벽 허용 신청
왜 이렇게
두 서비스가 같은 단계(연결)에서 동시에 실패했다는 점에서 코드보다 네트워크를 먼저 의심했습니다. 로그부터 제대로 보이게 만든 뒤에 판단했습니다.

"연결 실패"와 "응답 오류"는 다른 문제입니다. 어느 단계에서 실패하는지가 원인 범위를 정합니다.

#7집행액이 정확히 2배 — 1:N 조인에서 합계가 불어나고 있었다학교급식 · 보조금 관리›
증상

원인
같은 학교 · 연도에 배정액이 2건 등록되면, 배정액 기준으로 집행액을 조인하면서 집행액이 배정 건수만큼 중복 합산. 개발 DB에는 이전 버전 프로시저가 남아 있어 수정이 반영되지 않은 것처럼 보이기도 했음
해결

#8일부 연구자만 저장 실패 — 문자열 연결의 4,000바이트 한도협업 시스템 · AI 검색용 텍스트›
증상
연구자 정보를 합쳐 AI 검색용 텍스트를 만드는 UPDATE가 내용이 많은 연구자에서만 ORA-01489, 이후 ORA-06502
원인
CLOB 필드를 잘라 ||로 이었는데 연결 결과가 VARCHAR2로 계산돼 SQL 한도(4,000바이트)를 넘음. TRIM()도 CLOB을 VARCHAR로 바꾸고 있었음
해결
각 조각을 TO_CLOB()으로 감싸 CLOB 연산으로 바꾸고, 필드별로 1,000자씩 잘라 최종 4,000자로 제한
왜 이렇게
필드별 상한을 둔 것은 초록 같은 긴 필드 하나가 검색 텍스트를 독점하지 않게 하기 위해서입니다. 대신 AI 매칭에 반영되는 텍스트가 필드당 1,000자로 제한된다는 한계를 문서에 남겼습니다.
배운 점
일부 행에서만 나는 오류는 데이터 길이 · 타입 한도를 먼저 의심합니다. 연결 연산의 결과 타입은 피연산자가 정합니다.
#9여러 건 저장 시 일련번호 중복 — INSERT ALL에서 시퀀스는 한 번만 돈다협업 시스템 · 연구자 프로필›
증상
학력 · 경력을 여러 건 한 번에 저장하면 같은 일련번호가 들어가 PK 위반
원인
INSERT ALL … SELECT 1 FROM DUAL에서 NEXTVAL은 원본 행 하나당 한 번만 평가되어 모든 행이 같은 값을 받음
해결
서비스에서 목록을 돌며 한 행씩 INSERT. 목록 길이가 달라도 안전하게 인덱스 범위 확인
왜 이렇게
학력 · 경력은 한 번에 많아야 수십 건이라, 한 문장 최적화보다 행마다 고유 번호를 보장하는 단순한 방식을 택했습니다.
배운 점
여러 행을 한 문장으로 넣는 최적화는 시퀀스처럼 "행마다 달라야 하는 값"과 충돌할 수 있습니다.
#10논문 목록 10초 이상 — 이메일로 찾으면 빠르고 사용자 ID로 찾으면 느렸다협업 시스템 · 논문 조회›
증상
연결된 논문 수와 상관없이 목록 조회가 10초 이상
원인
  • 팝업에 필요 없는 저자 집계 · 초록까지 전체 조회
  • 행마다 도는 상관 서브쿼리
  • 사용자 ID로 조회할 때마다 사용자 뷰를 다시 탐색
해결
불필요한 컬럼 제거, 상관 서브쿼리를 사전 집계로, OR 조인을 EXISTS로, 저자 집계는 대상 논문에만. 외부 전체 조회는 이메일 기준으로 변경하고 인덱스 DDL 추가
왜 이렇게
"이메일로 검색하면 금방인데 사용자 ID 검색은 오래 걸린다"는 관찰에서 병목 위치를 좁혔습니다. 다만 저장된 프로필을 읽는 조회까지 바꾸자 미리보기가 사라져, 그 부분은 사용자 ID 기준으로 되돌렸습니다.
배운 점
같은 결과를 내는 두 조회의 속도 차이가 가장 좋은 단서입니다. 최적화는 적용 범위까지 확인해야 합니다.

#11고쳤는데 화면이 그대로 — 빌드 결과와 실제 서빙 폴더가 달랐다학교급식 · Nexacro 배포›
증상
화면 소스를 수정 · 생성(Generate)했는데 브라우저에 반영되지 않음. 생성본을 직접 고치자 오류가 연쇄로 발생
원인
생성 결과는 프로젝트 폴더에 쌓이지만 Tomcat은 Eclipse 배포 폴더(WTP)를 서빙. 두 위치 파일의 수정 시각과 해시가 달랐음. 이후에는 304 캐시가 겹침
해결
생성본은 손대지 않고 원본(.xfdl)만 수정 → 생성 → 배포 폴더 동기화 → 해시 비교로 반영 확인. 꼬인 상태는 원본 기준으로 되돌린 뒤 다시 시작
왜 이렇게
생성본을 직접 고치면 다음 생성 때 덮어써져 같은 문제가 반복됩니다. "어느 파일이 실제로 서빙되는지"를 해시로 먼저 증명하고 고쳤습니다.
배운 점
"반영이 안 된다"는 코드 문제가 아니라 배포 경로 문제일 때가 많습니다. 소스와 생성물을 구분하는 규칙을 팀 작업 방식으로 정했습니다.
#12같은 입력인데 C#과 Python 결과가 다름 — 정수 변환 차이열에너지 계산 플랫폼›
증상
히트펌프(WSHP) 계산에서 같은 설계 조건인데 C# 원본과 Python 이식본의 결과가 다름
원인
수식을 한 줄씩 비교한 결과 두 언어의 정수 변환 방식 차이로 중간값이 달라짐
해결
형변환을 C# 원본과 같은 의미로 수정. 이후 새 로직은 반영할 때마다 같은 입력으로 C# 결과와 대조
왜 이렇게
이식의 정답은 원본뿐이라, 코드가 비슷해 보이는지가 아니라 같은 입력에 같은 출력이 나오는지로 확인하는 절차를 만들었습니다.
배운 점
언어를 옮길 때는 문법보다 숫자 타입 · 반올림 · 나눗셈 규칙이 더 위험합니다.
#13한국어 Windows에서만 플러그인이 안 뜸 — SDK의 인코딩 미지정Synapse 플러그인›
증상

원인
synapse-sdk가 config.yaml을 인코딩 지정 없이 열어, 한국어 Windows에서는 시스템 기본값(cp949)으로 읽음

SDK 코드는 직접 고칠 수 없어 플러그인 쪽에서 피하고, 근본 해결(encoding="utf-8" 지정)은 기록으로 남겼습니다.
배운 점
파일을 열 때 인코딩을 생략하면 "내 PC에서는 되는" 코드가 됩니다.

AI와 일하는 방식

2026년 3월부터 실무에 Codex를, 이후 Claude Code를 써 왔습니다. 구현 속도는 AI에게서 얻고, 판단과 검증은 직접 합니다.

1. 근거를 준다에러 로그 · SQL 로그 · API 매뉴얼 · 사내 기존 코드를 원문 그대로 제공
2. 추정을 걷어낸다매뉴얼에 없는 추정 로직은 빼고, 공식 코드표 기준으로 교체
3. 범위를 정한다"원인만 분석", 공통 파일 · 운영 DB는 요청할 때만, 반영 전 백업
4. 숫자로 확인한다프로시저 결과 vs 테이블 직접 합계, 해시 비교, 컴파일 상태
A

AI의 계산 방식을 되돌린 사례

주문금액이 안 맞을 때 AI는 "최종 − 차액"으로 거꾸로 계산하자고 했습니다. 원본 기록 없이 숫자만 맞추는 방식이라 거절하고, 이력이 쌓이는 일괄처리 쪽을 고치게 했습니다.

B

과설계를 단순하게

검색 성능을 위해 AI가 캐시와 50건 선조회를 제안했지만 첫 검색이 더 느려졌습니다. "페이지마다 10건씩 호출"로 되돌렸고, 그게 현재 운영 구조입니다.

C

운영 반영은 사람이

"원인만 알려 달라"고 했는데 AI가 DB를 바로 수정한 일이 있어 즉시 원복시켰습니다. 이후 운영 DB에는 읽기 전용 조회만 연결하고, 구조 변경은 백업 후 개발 DB에서 검증한 뒤 반영합니다.
